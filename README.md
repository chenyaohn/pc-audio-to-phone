# 电脑音频 → 手机（低延迟）

把电脑正在播放的声音，实时转发到手机浏览器里播放。不装手机 App，不用编解码，
局域网内端到端延迟可以压到 **60–100ms**（USB 网络共享 + 15ms 缓冲时最低）。

文件：
- `pc_audio_to_phone.py` —— 采集 + 转发服务（Python）
- `index.html` —— 手机端页面（改完直接刷新浏览器即可生效，不用重启脚本）

## 一、跑起来

```powershell
pip install soundcard numpy websockets
cd <本文件夹>
python pc_audio_to_phone.py
```

启动后会打印手机要打开的地址，例如 `http://192.168.1.2:8720/`。

- 第一次运行 Windows 会弹防火墙提示，**必须点“允许”并勾选专用网络**，否则手机连不上。
- 找不到设备时先看清单：`python pc_audio_to_phone.py --list-devices`
- 想指定输出设备：`python pc_audio_to_phone.py --device Realtek`（名称模糊匹配）
- 手机上：打开地址 → 点「开始播放」（必须有一次点击，浏览器才允许出声）。

## 二、把延迟压到最低（按收益排序）

1. **用手机的 USB 网络共享**，让电脑走 USB 上网。此时启动时会多出一个类似
   `192.168.42.x` 的地址，用那个地址访问。信号稳定后可以把目标缓冲调到 15ms。
2. **手机不要连蓝牙耳机/音箱**。蓝牙 A2DP 自己就会再加 150ms 以上。
3. **用 Chrome**，页面保持在前台，别让手机自动锁屏（切后台/息屏浏览器会暂停播放）。
4. **目标缓冲**：从 30ms 往下试，出现断续就把数值加 10–20ms，找到你网络下的最低稳定值。
   页面上会实时显示缓冲、欠载次数和估算端到端延迟。

### 实测数据（本机，48kHz 立体声）

| 项目 | 实测 |
| --- | --- |
| 采集块大小/节奏 | 480 帧 (10ms)，间隔中位数 9.99ms，p95 12.6ms |
| 网络包 | 每包 1920 字节，100 包/秒，约 1536 kbps |
| 页面上行/下行稳定性 | 丢块 0、欠载 0（30ms 缓冲，连续运行） |
| 端到端估算 | 约 84ms（其中手机/浏览器输出缓冲占大头） |

延迟构成大致是：采集 10–15ms ＋ 网络（USB 1–5ms / WiFi 5–20ms）＋ 抖动缓冲 15–30ms
＋ 浏览器输出缓冲 20–40ms。**最后一项是硬下限**，任何方案都躲不掉。

## 三、常见问题

**手机打不开页面**：九成是防火墙没放行，或者手机和电脑不在同一个网段（比如电脑连了
有线、手机连了 WiFi 但路由器开了 AP 隔离）。也可以临时换成 USB 网络共享。

**有连接但没声音**：确认电脑上真的在播放声音（页面会显示电平和“收包”在涨）；
确认页面音量不是 0；确认点过「开始播放」。

**听音乐正常，但看电脑上的视频对不上口型**：声音走手机后必然比画面晚一个“估算延迟”。
在播放器里把**音频延迟调成负值**补偿即可，例如 mpv：
`mpv --audio-delay=-0.08 视频`，VLC 用热键 J/K 每次调 50ms 到 −100ms 左右。

**页面显示“当前没有音频在播放”**：这是正常的。Windows 在无声音时会以 40ms 一批补静音块，
一开始播放声音就自动回到 10ms。

**iPhone 能用吗**：能用（Safari/Chrome 打开同一个地址），但 iOS 浏览器的音频输出延迟通常比
安卓 Chrome 高一些，且必须保持页面在前台。

**音质**：全程 16bit 裸 PCM 直传，没有任何有损编码，音质等于原始播放。

## 四、参数

| 参数 | 说明 |
| --- | --- |
| `--port` | 端口，默认 8720 |
| `--device` | 采集哪个输出设备的回环（模糊匹配名称） |
| `--rate` | 采样率，默认 48000（手机硬件原生，避免重采样） |
| `--synthetic` | 不采集真实音频，发测试音，用来先验证链路 |
| `--list-devices` | 列出所有播放/回环设备 |
| `--no-boost` | 不做 Windows 调度优化（默认会提高优先级、缩短定时器粒度） |

## 五、原理与取舍

```
WASAPI 回环采集 → float32 → int16 裸 PCM → WebSocket(TCP_NODELAY)
                                   → 手机浏览器 Web Audio 手动排程
```

- **不做编码**：局域网带宽足够（1.5Mbps），省掉 Opus 编解码的 5–15ms 和一层缓冲。
- **不用 `<audio>` 标签**：它自带几百毫秒缓冲；这里把每块音频挂到 Web Audio 的时间轴上，
  缓冲完全由页面的「目标缓冲」决定。
- **±6% 速率微调**：电脑声卡时钟和手机声卡时钟不可能完全一致，不修正的话几分钟就会漂移
  几十毫秒。页面用极小的速率调整把缓冲一直锁在目标值附近，听感上察觉不到。
- **丢包策略**：服务端每台手机只留 2 块待发数据，来不及就丢最旧的——宁可少一点音频，
  也不让延迟越积越多。

## 六、已知限制

- 走 TCP，WiFi 严重丢包时会出现短暂卡顿（可用 USB 网络共享规避）。若要更强的抗丢包，
  下一步可以换 WebRTC（Opus + 内置抖动缓冲）或 WebTransport 数据报。
- **没有鉴权**：同一局域网内知道地址的人都能听到声音。介意的话可以加个 token 校验。
- 只做本机回环采集；如果电脑上有独占模式（唯 WASAPI 独占）播放的软件，可能采集不到。
